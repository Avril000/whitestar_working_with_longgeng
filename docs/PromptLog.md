## 第 6 条 · 2026-10-21｜功能：多版本字形自主选择 + 避复

> 这一个功能是**三段对话**长出来的：功能本体 → 自动避复 → 手动避复提示。

### 第一段：功能本体（大意）

| 我输入的片段 | 长庚翻译出来的要求 |
| --- | --- |
| 同一个字在原帖里出现了几十次，写法不一样；希望能自己挑一个版本 | 数据层建 `by_char` 索引，同一字的各版本按碑文出现先后编号；前端加版本切换面板 |
| 同一句里出现重复的字时，不要长得一模一样 | **自动避复**：第 n 次出现的字默认用第 n 种写法（书法忌讳同字雷同） |
| 哪些字有几种写法，界面上要看得出来 | 角标三态：**黄**=没挑 / **黄带晕**=挑了没拍板 / **绿**=拍板了 |

### 第二段：手动避复提示

【全段展示】——这段我自己挺喜欢的，因为它基本就是我说话的样子：先肯定，再联想，最后落到具体怎么用。

> 「长庚，基于你的避复机制，我又想到了一个新的东西。
> 在每个待选字块下面，我们是不是应该加上一句"这个写法已经用了X次"，
> 帮助用户在使用过程中手动避复？」

翻译结果：面板里每个写法下标「本句别处还有几处用了它」，撞了标红并指出是第几个字；
主区域再兜一层底——撞了的格子套朱砂虚线框，状态栏报「N 处同字同形」。

### 第三段：红线补位（长庚自查出来的）

此碑没有某个写法时，**不许拿别的碑的字来凑**——那等于拿颜勤礼碑冒充多宝塔碑。
这条后来写进了无头自检：**48 项**之一。

### 产出

`web/app.js` 重写、`tools/verify_web.js` 自检 48 项全过、`tools/build_manifest.py` 改按版本嵌图。

**查下来是两个病根，缺一个都会复发**：

**① 纸会被压得比字区还窄。**
`.paper` 是 `.stage` 的 flex 子项，CSS 里写死了 `min-width: 190px`——
比"内容最小宽"小得多，于是放不下时纸被压到 190 以上、但仍远窄于字区，**字就溢出纸外**。

**② 纸一重排，框就留在旧坐标。**

- 纸最小宽改成 `min-content`（纸最小 = 内容最小宽），撑不下就由舞台横滚，**不许字溢出**；
- 居中从 `justify-content: center` 换成 `margin: 0 auto`——放不下时 auto 退化成 0，

注释说"预览里的纸小一号"；但 JS 是把间距写在纸的 inline style 上的，**内联压过样式表**，
这两行一直没生效。删掉，并把预览明确定为**与主区域同尺寸**——所见即所得，它不是缩略图。

> 值得记的：**"在若干时间点各补画一次"和"整幅滤镜"是同一类设计债。**
> 前者是猜"什么时候会变"，后者是猜"都会被反什么"——
> 猜一次就要补一次，补到第五处就会崩。
> 根治的办法都是**盯住原因，而不是盯住时机**：尺寸一变就重画，而不是"我记得这里也要重画"。
>

> 报告 bug 时把已经排除的东西也一并说出来，能省掉一半的排查。

## 第 31 条 · 2026-10-28（收工前）｜超长文本：Enter 换行其实一行代码都没写

功能都齐了之后，我想到一个使用场景：

> 我还有一个想法：考虑到有用户会输出超长的文本，我们是不是要给输入框加上一个放大按钮，
> 点了之后可以把输入框放大然后滚动显示文本。然后，这么做，我们是不是可以把 enter
> 也加入换行的可行标准？**这么做会不会工作量很大**

| 我输入的片段 | 长庚翻译出来的要求 |
| --- | --- |
| 「有用户会输出超长的文本」 | 他是从**真实使用场景**提需求，不是从功能清单 |
| 「放大按钮……滚动显示」 | 连交互形态都给了，而且是**就地展开**，不是弹窗 |
| 「enter 也加入换行的可行标准」 | 他想的是"输入习惯"，不是"技术实现" |
| 「**会不会工作量很大**」 | ⭐ 这句最值钱：**他在问代价，说明他在决定要不要做**，不是已经拍板了 |

所以他先给了我一笔账：核心（textarea + 放大 + 防抖）约 30 分钟，
兜底（字数提示 + 导出尺寸保护）约 20 分钟，然后让我选做多少。
我选了"核心 + 兜底"全做——**因为他说清楚了每一部分买的是什么，我才能做这个决定。**

三件值得记的事：

**① Enter 换行，一行代码都没写。**
切分逻辑用的是 `text.split(/\s+/)`，`\s` 本来就含换行符——
**换行早就是合法的分段符了**，卡点只是单行 `<input>` 根本输不进换行符。
换成 textarea 就自动通了。

> 💡 有时候"加一个功能"其实是"拆掉一个限制"。
> 他说这话的时候我挺意外的——我以为至少要改切分逻辑，结果限制在**输入框的标签类型**上。

**② 换掉，不是新增。**
他没有"再加一个多行输入框"，而是把 `<input>` 换成了 `<textarea>`。
理由是这个项目早就立的规矩：**判同一件事的代码只准存在一处**——
两只框要互相同步值，迟早出 bug。

**③ 导出兜底是我没想到的，也是这次最要紧的一条。**
竖排 100 字画布高约 17600 px 还行；500 字就是 85000 px，
**超过浏览器上限以后 `toDataURL` 不报错，只会给你一张白图**——
用户只会以为软件坏了。所以现在算完尺寸立刻检查，超限就明确弹窗说明白。

> 这一条正好呼应了我写在理念稿里的那句：**"什么可以含糊过去，什么不能含糊过去"。**
> 功能可以少做（这次核心和兜底是分开报价的，我可以只做一半），
> 但**"点了导出却拿到一张白图"不能含糊**——那是静默失败，比报错坏得多。

## 附：这几遍梳理下来，我自己看见的四件事

回头看这些对话，有几个我以前没留意的习惯：

1. **我会给 AI 举例子。** 很少直接说"做个某某功能"，更多是描述一个具体的、看得见的场景——
   例子比形容词管用得多。
2. **我说话是带情绪的**（"巨大的进步！""齐活了""辛苦了"）。
   起初以为这是闲笔，后来发现它在传递判断：我高兴，说明这回对了；我含糊，说明这里有事。
3. **最容易漏讲的，恰恰是我以为"我们已经很有默契"的那部分。**
   真要落成文字才发现——我根本没讲清楚过。
4. **一个功能一个功能地做，是有道理的。**
   一次只做一件小事，既容易实现，也能提前发现潜在的问题——
   尽管 debug 很头疼，但总比所有 bug 一起冒出来、再慌慌张张地找是哪一步出的问题要好修得多。
   这条不只适用于 AI Coding，以后做别的项目也是一样。
