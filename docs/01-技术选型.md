# 01 · 技术选型：到底要不要"后端"

> 写给你和小组成员看。不需要技术背景，读完能拍板。

## 一、先讲清楚两个词

**"运行期"** —— 汇报那天，打开给大家看的那个东西。它要当场跑、当场出结果。

**"构建期"** —— 我们在自己电脑上、汇报之前跑的加工程序，比如把一整页碑帖图片裁成一个个单字。它跑一次，结果存下来，之后就不用再跑了。

这两个阶段**可以用不同的技术**。这是本次选型的关键。

## 二、三个方案对比

| 方案 | 怎么运作 | 优点 | 风险 |
| --- | --- | --- | --- |
| **A. 纯前端** | 一个网页 + 图片 + 数据表，所有计算在浏览器里做 | 双击就能开，不装任何东西，断网也能跑 | 做不了重活（图像处理、AI 算法基本没戏） |
| **B. 前端 + 后端服务** | 网页发请求给本机 Python 服务，服务端做计算 | 什么都能做 | 汇报现场必须先启动服务、必须装好 Python；投影电脑环境未知，**翻车风险最高** |
| **C. 构建期 Python + 运行期纯前端** | Python 只在我们电脑上跑，把活干完、结果存成 JSON；网页只读现成结果 | 既拿到 Python 的全部能力，又保证现场零风险 | 数据更新要重跑一次脚本（很轻） |

## 三、推荐方案 C（强烈推荐）

一句话：**用 Python 当"加工厂"，用网页当"成品"。**

```
碑帖大图 ──► Python 脚本（裁字/去背/算相似度）──► 单字图 + 字形表.json ──► 网页直接读取展示
  构建期           我们电脑上跑一次                      落盘产物              运行期（零依赖）
```

### 为什么是它

1. **演示零风险。** 汇报那天只要一个文件夹：一个 HTML + 若干图片 + 一个 JSON。双击即开，不断网也能跑，老师的电脑也能跑。这是 B 方案给不了的。
2. **照样拿"真技术"分。** 评分表进阶层要求"至少一项真技术：真图 / 真 OCR / 相似度 / 图算法 / 检索 API / 大模型 API"。我们的自动裁字、去背景、字形相似度计算，都是**真图 + 相似度**，稳稳落在这一格。
3. **正对挑战层的"可自动化管线"。** 挑战层数据规模写的是「>100 条；**或者可自动化管线持续扩充**」。我们有一条能反复跑的管线——字形不够了，跑一遍脚本就扩充，这条比单纯堆数量更有说服力，两个都占。
4. **队友友好。** 5 个人里不需要人人配 Python 环境。想改数据就改 JSON，想看效果就开网页。

### 为什么不选纯后端（B）

- 现场要起服务、要装环境，新手 + 陌生电脑 + 时间压力 = 高风险。
- 5 个新手维护一整套前后端，调试成本直接翻倍，而收益我们已经在 C 里拿到了。

## 四、具体技术栈

### 运行期（网页，零依赖）

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 结构 | 原生 HTML + CSS + JavaScript | **不用 Vue / React**，新手看不懂也改不动 |
| 外部库 | **零** | 不用任何 CDN。汇报现场可能没网，外链一断页面就废 |
| 竖排排版 | CSS `writing-mode: vertical-rl` + Flex | 浏览器原生支持，条幅 / 对联都靠它 |
| 导出图片 | Canvas（浏览器原生） | 把排好的条幅导出成 PNG，不需要额外库 |
| 字体 | 系统衬线字体（宋体 / 思源宋体） | 不依赖网络字体 |
| 配色 | 宣纸米白 + 墨黑 + 朱砂红 | 见下方"界面调性" |

### 构建期（Python，只在自己电脑上跑）

| 包 | 用途 | 安装 |
| --- | --- | --- |
| **PyMuPDF** | 把碑帖 PDF 逐页渲染成高清页图（10/19 实测后新增） | `pip install pymupdf` |
| **Pillow** | 读图、裁切、缩放、去背景 | `pip install pillow` |
| **NumPy** | 数值计算（相似度、二值化） | `pip install numpy` |
| opencv-python（可选） | 更聪明的自动切字（找字块轮廓） | `pip install opencv-python` |

> 三个包一行装完：`pip install pymupdf pillow numpy`
> 实测结论：中华珍宝馆与书格都交付 **PDF**，所以 PDF 渲染是管线的第一步。

只要这 2–3 个包，都是一行命令能装好的常用库。

### 数据格式

**JSON + PNG。** 理由：JSON 是纯文本，队友能直接用记事本打开改，老师也能看懂；我们不需要数据库。

## 五、算法这个格子怎么填（冲挑战层）

按难度从低到高，我们按顺序做：

| 优先级 | 算法 | 做什么 | 难度 |
| --- | --- | --- | --- |
| **必做** | 自动切字（连通域 / 投影切分） | 从整页碑帖里自动找出每一个字的位置并切出来 | 中 |
| **必做** | 图像二值化 + 去背景 | 把拓本的灰底去掉，得到干净的黑字白底（或透明底） | 低 |
| **必做** | 字形相似度（感知哈希 / 特征比对） | 缺字时推荐"形近字"、判断"同碑他字"像不像 | 中 |
| 加分 | 偏旁拼合 | 课题里点名的缺字处理方案之一，能做出来是亮点 | 高 |
| 可选 | 大模型 / OCR API | 出处核验辅助 | — |

**关于 API 的重要提醒：** OCR、大模型这类需要联网的接口，**只能当辅助，不能当核心依赖**。汇报现场断网，依赖它的功能就当场失效。所有联网能力必须设计成"没有也能跑完整流程"。

## 六、界面调性（这一项直接影响"界面专业美观"这一档）

碑帖题材，界面本身就是作品的一部分。建议：

- **底色**：宣纸米白（#F5F1E8 一类），不用纯白
- **主色**：墨黑（#1A1A1A），**点缀**：朱砂红（#9E3D32）
- **字体**：标题与正文用衬线（宋体系），营造碑刻感
- **集字区**：竖排右起，字距略大于行距，模拟真实条幅
- **缺字标记**：明确可见的朱砂框 + 「缺」字角标，让人一眼看出这是缺的，不是排版失误
- **核对状态**：用三种可区分的视觉标记（已核对 / 存疑 / 未核对），并在图例里说明

## 七、补充：演示环境已确定（10/16 更新）

新增两条信息：

1. **汇报可以自带电脑**，演示环境以本机为准
2. **班级有一台共享服务器**（`81.71.14.93`，2核4GB，每人一个端口）

### 这两条对选型的影响

第一条**降低了方案 B（前端 + 后端）的风险**——既然是自己的电脑，Python 环境是配好的，起 Flask 服务可行。

**但我仍然推荐方案 C，理由反而更强了：**

方案 C 的成品是**纯静态文件**（HTML + 图片 + JSON），所以：

| 方案 C 的同一份文件 | 方案 B |
| --- | --- |
| 本地双击 `index.html` → 能跑（主轨，永远可用） | 本地要起 Flask 服务 |
| 丢到服务器上 `python3 -m http.server` → 也能跑（副轨，在线加分） | 服务器要另配环境 |

**一份产物，两个通道，零改动。** 而方案 B 要维护两套、部署两次、多一层依赖。
对 5 个新手的队伍来说，能少一层就少一层。

> 服务器详见 [docs/06-服务器使用方案.md](06-服务器使用方案.md)。
> 核心原则：**在线版是加分项，本地版才是保命项。**
