我们与 AI 的协作开发手册

移动信息化 · 课堂研讨 · 课题 19「碑帖集字生成器」　|　第 1 版　|　2026-10-15

协作流程分工契约可发队友

这份手册回答一个问题：用 AI 开发一个软件，到底要走哪几步、每一步谁干什么。 它不是技术教程，而是我们这支队伍（你们 + 长庚）的分工契约。建议小组第一次开会时一起过一遍。

一、先破一个误区

AI 开发 不等于 把需求丢给 AI、然后等结果。

更准确的关系是：你们是甲方 + 品控，AI 是施工队 + 技术顾问。 AI 出力气、出速度、出技术细节；但做什么、做到什么程度、结果对不对，这三件事只能你们拍板。 尤其这次课题里反复强调「缺字必须报缺字」「绝不允许悄悄用其他来源的字冒充原帖」—— 这其实是在提醒：AI 最大的风险不是做不出来，而是"编得很像"。

二、六个环节

1准备 Setup
环境、分工、素材、评分规则，一次摆上桌
2定义 Define
把模糊想法，写成可勾选、能验收的清单
3设计 Design
选型、数据结构、页面草图、里程碑拆分
4建造 Build
一次只做一个功能，跑通了再叠下一个
5验证 Verify
报错原文回传；功能、文化、界面三查
6交付 Deliver
现场演示、汇报 PPT、课程论文、Prompt Log

1–3 是开工前，4–5 是反复循环的小轮子（做一块、验一块），6 之前往往会回炉重来。

三、每个环节的三方契约

环节你们给我长庚给你们只能你们判断
1 准备 组员名单与想承担的角色；每人电脑情况（系统、是否已有 VS Code / Python / Node）；汇报日期与期末 DDL；目标层次（保底 / 良好 / 优秀） 环境体检清单 + 一步步安装命令；项目目录骨架；3–4 人分工建议模板；从评分表反推的工作量地图 谁干什么（按兴趣和时间，不是硬分）；能投入多少时间；目标定哪一档——这一条决定后面所有工作量
2 定义 一句话想法，越具体越好；真实使用场景（谁、在哪、怎么用）；界面草图（手画拍照、截图拼贴都行）；硬约束（哪些事绝对不能做） 分三档的需求清单：必须做 / 最好有 / 明确不做；验收标准：怎样才算做完；取舍建议与风险提示 砍需求——最疼也最关键的一步；确认验收标准；把文化红线写进需求（如：缺字必须如实报缺字）
3 设计 确认过的需求清单；数据来源偏好；技术倾向（纯前端还是要后端） 技术选型对比（含各自代价）；数据结构：每条字形记录有哪些字段；页面线框图；里程碑拆分 拍板选型；确认数据字段——这是地基，后面改最贵；确认里程碑顺序
4 建造 一次只提一个功能；收到代码后立刻运行，把真实结果告诉我；报错原文——复制粘贴，不要转述 可运行的增量代码；每版改了什么、已知问题有哪些；下一步建议 每跑通一个功能就存档一份；说「这里够好了，进下一个」，别无限打磨；发现方向不对立刻叫停
5 验证 出错截图 / 控制台报错原文；「这里看起来不对」的具体描述；文化质疑（这个字真的出自这个碑吗） 修复 + 原因解释（不只是改好）；自查清单与边界测试用例；性能与文化准确性复查 文化准确性——AI 最容易在这里编得像是真的；界面审美与字体排版；现场演示走一遍，卡在哪就记下来
6 交付 汇报时长与想讲的技术点；各人实际贡献；≥5 条关键 prompt 的记录 汇报 PPT 大纲与制作；技术报告骨架（6–12 页）；Prompt Log 整理成表；演示脚本与台词建议 谁上台、练几遍；演示必须真跑通，不录屏；所有数据标注来源与核对状态

四、五条反直觉常识

  1. 描述给得越具体，AI 做得越准。「做个集字器」能做出 10 种；「输入『江山如画』，从《九成宫》取字，竖排条幅预览，缺字弹窗报缺」——做出来就是你们要的那个。
  2. 报错要丢原文，别转述。「它报错了」我得猜；把红字整段复制过来，一眼就能定位。转述时丢掉的那半句，往往正是病因。
  3. 一次只做一个功能。一口气要 5 个功能，会得到 5 个「看起来能跑」的半成品。
  4. AI 会编，而且编得很像。这是本次课业最大的风险点。所有字形出处、朝代、碑名，必须人工核到原始来源，不许 AI「合理推测」。
  5. 跑通了就存档。每完成一个能用的版本就复制一份。新手最大的痛不是做不出来，是改崩了回不去。

五、开工前要准备的六样东西

  • 队伍：组员名单、各人想做什么、每周能投入多少时间、怎么联系
  • 环境：每人一台能开浏览器的电脑；推荐 VS Code（编辑代码）+ Git（版本存档，可选但强烈建议）
  • 时间线：课堂研讨汇报日期、期末论文 DDL、中间几个检查点
  • 目标档位：基础层（保底合格）/ 进阶层（良好）/ 挑战层（优秀）——三档工作量差很多，必须先定
  • 素材与数据源：课题说明文件（已有）、碑帖底本的选择意向、可用数据源清单（手册附录）
  • 记录工具：一个共享文档，用来记 Prompt Log（课程要求 ≥5 条关键提示词迭代）与分工实绩

六、课题 19 速览与得分点

任务目标（原文摘要）

用户输入一句话（如「江山如画」）并选择底本碑帖 → 系统从已标注的字形库里取出对应单字 → 排成条幅 / 对联预览。

硬约束：库里没有的字必须明确报「缺字」，并列出可选处理方案（换底本、留空、用同碑他字、以偏旁拼合）；每种方案在视觉与元数据上都可区分；绝不允许悄悄用其他来源的字冒充原帖。

评分维度基础层（合格）进阶层（良好）挑战层（优秀）
数据规模最小样例 10–30 条真实来源，>60 条>100 条，或有可自动化管线持续扩充
数据真实性自动爬取或人工整理逐条标来源与核对状态抓取→清洗→校核→入库全流程清晰完整
工程深度纯简单前端、数据写死前端功能完整 + 界面美观 + 简单算法技术创新 / 功能完整 / 界面专业美观
智能 / 算法规则匹配、简单渲染、有界面至少一项"真"技术：真图 / 真 OCR / 相似度 / 图算法 / 检索 API / 大模型 API实现或应用某个先进 AI 算法并成功落地
评价格式说明：达到基础层即合格；4 个维度中有 3 个达到进阶层，即可考虑评为良好；同理 3 个维度达到挑战层可考虑优秀。
提交物：① 现场汇报 PPT + 软件作品演示　② 课程论文（技术报告，建议 6–12 页，Word & PDF）　③ 可运行软件 + 说明文档 + 代码压缩包　④ 过程材料：Prompt Log（≥5 条）、迭代截图、分工说明。

先记着这三个词后面会反复出现：核对状态、缺字报告、不允许冒充。 它们既是评分点，也是我们这个作品最值得讲的地方——「一个诚实的集字器」本身就是一个好选题。

七、第一次小组会议：30 分钟拍板这 5 件事

  1. 目标档位：冲哪一档？（决定后面所有工作量）
  2. 分工：谁做需求与汇报、谁做数据与考据、谁跟我写代码、谁管文档与 Prompt Log
  3. 底本碑帖：先定 1–2 种（决定了字形库往哪个方向建）
  4. 时间线：汇报日期倒推，定 3 个中间检查点
  5. 沟通方式：建个群 / 共享文档，所有 prompt 与产出都往里丢
